```

    - 저장소 구조: `include/`(헤더), `test/`(GTest), 루트 `CMakeLists.txt`
    - 기술 스택: C++17, CMake 3.14+, FetchContent로 Google Test/Google Mock v1.14.0, `gtest_discover_tests`
    - 도메인: 일반 채널 0~99, `remoteKey` enum, `TVController::pushButton(remoteKey)`
    - 외부(Tuner 업체) 제공: `include/Tuner.h`의 `Tuner` 인터페이스 — `seekCH()`, `setCH(const std::string&)`, `getCurrentCH()` (채널은 문자열)
    - 우리가 구현·테스트하는 대상: `TVController` 및 `remoteKey` 확장; Tuner 구현체 직접 작성·단위 테스트 금지
    - 요구사항 출처: `README.md`의 숫자/확인/선호채널/다음선호/채널검색/업·다운 동작 명세

[T] 아래 요구를 만족하는 `.cursorrules` **전체 본문**을 작성해줘. (메타 설명·서두 말 없이 파일 내용만)

    1) 프로젝트·빌드
       - C++17, CMake 표준 준수, `include/` 경로 사용
       - 테스트 실행: configure 후 `ctest` 또는 GTest 타깃(`TunerTest`, `TVControllerTest` 등)

    2) 절대 규칙 (변경·위반 금지)
       - `include/Tuner.h`의 `Tuner` 클래스 시그니처·가상 메서드 계약 수정 금지
       - Tuner는 항상 정확히 동작한다고 가정; Controller 테스트는 Mock 또는 Fake로 `Tuner`를 대체
       - 채널 유효 범위: 0~99 (문자열/정수 변환 시 경계 포함)
       - Samsung 저작권 헤더 블록이 있는 파일에서는 해당 블록 삭제·변형 금지

    3) TDD·구현 규칙
       - Red → Green → Refactor: 실패 테스트 추가 → 최소 구현 → 테스트 Green 유지하며 리팩토링
       - 리팩토링·기능 추가는 **모든 관련 테스트가 Green일 때만** 진행
       - `TVController`는 생성자 주입 `Tuner*` 유지, 하드코딩된 실제 Tuner 구현에 의존하지 않음
       - `README.md`에 없는 동작은 임의 추가하지 말고, 불명확하면 테스트 이름·주석으로 가정을 명시

    4) 테스트 규칙
       - Google Test + Google Mock 사용
       - 테스트 이름·구조: Given-When-Then 의도가 드러나게 (한글 또는 영문 명확한 `TEST_F`/`TEST` 이름)
       - Controller 테스트: `MockTuner` 또는 `FakeTuner`로 `setCH`/`getCurrentCH`/`seekCH` 기대 설정
       - `EXPECT_CALL`로 Tuner 호출 검증; 로그(`std::cout`) 출력은 assert하지 않음
       - README 시나리오별 최소 1개 이상 테스트 (숫자 입력·확인, 연속 숫자, 선호채널 토글, 다음 선호, 채널검색 저장, 업/다운 with/without 검색 결과)
       - 경계값: 채널 0, 99, 0↔99 래핑, 잘못된 채널 입력(Tuner가 `invalid_argument`를 던지는 경우는 Mock으로만 검증)

    5) 코드 스타일·구조
       - 헤더 가드·기존 네이밍(`remoteKey`, `TVController`, `processingCH` 등)과 일치
       - 매직 넘버(99, 0 등)는 named constant로 정리 권장
       - 구현은 우선 `include/*.h` 인라인/헤더 중심(별도 `src/` 없음) — 기존 패턴 유지
       - `remoteKey` 및 `to_string(remoteKey)`는 키 추가 시 switch 일관성 유지

    6) AI 작업 시 금지·주의
       - `build/` 산출물·`_deps/` 수정·커밋 제안 금지
       - Tuner 실제 구현 파일을 새로 만들어 프로덕션에 넣지 말 것 (테스트용 Mock/Fake만)
       - 사용자가 요청하지 않은 대규모 리네이밍·포맷 전체 변경 금지
       - 커밋·PR 생성은 사용자가 명시적으로 요청할 때만

    7) (선택) 커버리지
       - 본 프로젝트 CMake에 gcov/lcov가 없으면 언급만 하고, 추가 시 `-fprofile-arcs -ftest-coverage` 등은 별도 브랜치/요청 시에만 제안

[F] 출력 형식
    - 마크다운 코드펜스 없이, `.cursorrules` 파일에 **그대로 붙여넣을 수 있는 평문**만 출력
    - 섹션은 `##` 제목 + 짧은 불릿으로 읽기 쉽게 구성 (한국어 위주, 식별자·API 이름은 영문 유지)
    - 분량: 실무에서 매일 참고할 수 있도록 80~150줄 내외 (과도한 장문 금지)
```

## 복사용 프롬프트

```
@README.md
@docs/requirements_analysis.md
@include/Tuner.h
@include/TVController.h
@include/remoteKey.h
@test/TunerTest.cpp
@test/TVControllerTest.cpp
@CMakeLists.txt
@.cursorrules

[P] 시니어 QA 리드입니다. TDD 사이클(Red→Green→Refactor)과 Google Mock 기반 단위 테스트 설계에 익숙합니다.

[C] TDD_TV_Init 프로젝트 (C++17, CMake 3.14+, Google Test/Google Mock v1.14.0, `gtest_discover_tests`)
    - SSOT: `docs/requirements_analysis.md` (비즈니스 규칙 §1, 모호성 §2, 경계 E1~E15, 시나리오 §6.1~6.2)
    - 구현 대상: `TVController`, `remoteKey` / 수정 금지: `Tuner` 인터페이스
    - 채널 도메인: `std::string` 0~99; Controller 테스트는 Mock/Fake (`TunerTest.cpp` 패턴)
    - 기존 타깅: `TunerTest`, `TVControllerTest` (`CMakeLists.txt`)
    - 검증 제외: `std::cout` 로그, Tuner 실구현·`TunerTest.cpp` 본문 수정
    - 커버리지: 현재 CMake에 gcov/lcov 미설정 → 계획서에 **선택 적용**으로 기술

[T] 아래 항목을 포함한 **테스트 계획서**를 작성해줘.

    1) 테스트 전략 요약
       - 단위 테스트 범위(In scope / Out of scope)
       - Mock vs Fake 사용 기준 (`Tuner` 계약 검증 vs Controller 행위 검증)
       - TDD 진행 순서(우선순위 P0/P1/P2): README 시나리오 1→6, 그다음 경계·모호 해소

    2) 테스트 구조·fixture 설계
       - `TEST_F` 기반: `TVControllerTest` fixture (`MockTunerForController`, `TVController`)
       - `TEST_P` / `INSTANTIATE_TEST_SUITE_P` 적용 후보 (채널 래핑, 유효 숫자 조합, `TunerTest.cpp`의 Valid/Invalid 채널 패턴 참고)
       - 파일·타깅 제안 (`test/TVControllerTest.cpp` 확장 vs 분리) 및 CMake 등록

    3) 단위 테스트 범위·우선순위 표
       - 기능 영역(§1.1~1.6)별: 테스트 ID | 우선순위 | 대응 requirements §6 시나리오 번호(1-1, 2-1, A1 등) | 검증 포인트 | Mock 기대 요약

    4) 경계값 케이스 목록 (표)
       - 채널: `0`, `1`, `99`, `0↔99` 래핑(업/다운, 검색 없음)
       - 숫자 입력: 1자리+OK, 2자리 즉시 확정, `0`+`7`→`7`, `9`,`9` 후 세 번째 숫자, 빈 버퍼+OK
       - 선호: 0개/1개/다수, 로테이션(현재 `56`→`1`)
       - 검색: `seekCH` 즉시 `""`, 단일 결과 `{6}`, 목록 외 현재 채널(`15`)
       - 분기: `searchResults.empty()` true/false에 따른 업/다운

    5) 예외·특이 케이스 목록
       - 미확정 버퍼 + 비숫자·비OK 키 → 무효화 (`4`,`5`,`6` 후 UP 등)
       - Controller 선검증으로 `setCH` 미호출(무효 채널)
       - `getCurrentCH` 무효 문자열 시 no-op (requirements E14)
       - `KEY_NEXT_FAVORITE` 선호 없음, `setCH` Times(0) 시나리오
       - Tuner `invalid_argument`는 `TunerTest` 영역, Controller 테스트와 역할 분리

    6) 시나리오 ↔ 테스트 케이스 매트릭스
       - `requirements_analysis.md` §6.1(1-1~6-4), §6.2(A1~A8) 각각에 대해:
         - 제안 `TEST_F`/`TEST_P` 이름(영문, Given_When_Then 스타일)
         - Given / When / Then (1줄)
         - `EXPECT_CALL` 핵심(메서드, Times, Return/Throw)

    7) TDD 실행 계획 (스프린트/단계)
       - Phase별: 추가할 테스트 목록 → 최소 구현 → 리팩토링 체크포인트
       - 각 Phase 완료 기준: `ctest` Green, 관련 시나리오 ID 전부 통과

    8) 커버리지 목표·측정·개선 전략
       - 목표: `TVController`·`remoteKey` 관련 코드 **라인 커버리지 90%+** (권장, 조정 가능)
       - 현재: gcov/lcov 미설정 → CMake 옵션 예시(`-fprofile-arcs -ftest-coverage`, `lcov`/`genhtml`) **부록**으로만 제시
       - 측정 범위: `include/TVController.h`, `include/remoteKey.h` / 제외: `Tuner.h`, 로그, `build/`
       - 미커버 구간 대응: 분기(검색 유/무), 버퍼 상태, 선호 토글 등에 대한 추가 `TEST_P` 제안

    9) 리스크·미결정 사항
       - requirements §2·E5·A8 등 **테스트에서 하나로 고정할** 항목과 결정안
       - 내부 상태(`favoriteChannels`, `searchResults`) 직접 검증 불가 시 호출 순서만으로 검증하는 한계

[F] Markdown 문서 (표 + 번호 목록). **파일로 저장**: 프로젝트 루트 `test_plan.md`
    - `docs/` 폴더가 팀 규칙상 문서 SSOT이면 `docs/test_plan.md`로 저장해도 됨(저장 경로를 문서 상단에 명시)
    - 상단: 프로젝트명, 작성일, 참조 문서(`requirements_analysis.md`, `README.md`)
    - §6 시나리오 ID와 계획서 테스트 ID를 1:1로 추적 가능하게
    - 실행 명령 예: `cmake -B build && cmake --build build && ctest --test-dir build`
```

## 복사용 프롬프트

```
@test/TVControllerTest.cpp
@test/TunerTest.cpp
@include/TVController.h
@include/remoteKey.h
@include/Tuner.h
@docs/requirements_analysis.md

[P] 디버깅과 결함 분석에 능한 C++ QA 엔지니어입니다. Google Test/Google Mock 실패 로그, `EXPECT_CALL` 위반, Mock 순서·Times 불일치를 읽고 생산 코드 결함과 테스트 결함을 구분합니다.

[C] TDD_TV_Init (C++17, CMake, GTest/GMock v1.16, `TunerTest` / `TVControllerTest`)
    - 생산 코드: `include/TVController.h`, `include/remoteKey.h`
    - 테스트: `test/TVControllerTest.cpp` (시나리오 ID `1-1`~`6-4`, `A1`~`A8` 주석)
    - SSOT: `docs/requirements_analysis.md`, `docs/test_plan.md`
    - **수정 금지**: `include/Tuner.h` 시그니처·계약, `test/TunerTest.cpp` (Tuner 계약 테스트)
    - 검증 수단: `EXPECT_CALL(setCH/getCurrentCH/seekCH)` — `std::cout`는 결함 판단에 사용하지 않음
    - 빌드·실행(로그 없을 때 직접 수행):
      ```
      cmake -B build && cmake --build build && ctest --test-dir build --output-on-failure
      ```
      실패 시 상세:
      ```
      ctest --test-dir build -R TVControllerTest --output-on-failure -V
      build\TVControllerTest.exe --gtest_filter=실패테스트이름
      ```

[T] 아래에 **ctest / gtest 실패 로그 전문**을 붙여넣을 것. (비어 있으면 위 명령으로 직접 실행한 뒤 분석)

--- 붙여넣기 시작 ---
(여기에 실패 로그)
--- 붙여넣기 끝 ---

실패 건마다 다음을 수행해줘.

    1) **실패 요약**
       - 실패 테스트명 (`TEST_F` / `TEST_P`) 및 requirements 시나리오 ID (`// 1-4b` 등)
       - 실패 유형 분류:
         | GMock `EXPECT_CALL` / `Times` / 인자 불일치 |
         | `EXPECT_EQ` / `ASSERT_*` |
         | Segfault / 컴파일·링크 |
         | 테스트 셋업(Mock `ON_CALL`/`WillOnce` 누락, `InSequence` 순서) |
       - **기대 vs 실제** (호출된 `setCH` 인자, `Times`, `seekCH` 횟수, 미호출 등)를 표로 요약

    2) **근본 원인 & 버그 위치**
       - `TVController::pushButton` 및 관련 private 헬퍼(`handleDigit`, `setTunerCh`, `channelUp/Down`, `toggleFavorite`, `nextFavorite`, `runChannelSearch` 등) 중 **결함 지점**
       - **파일명:줄번호** (가능하면 함수명)
       - README/requirements §2 권장 가정과 어긋난 동작인지 명시
       - **생산 코드 버그 vs 테스트 오류 vs Mock 기대 오류** 구분 및 근거

    3) **결함 심각도** (Critical / Major / Minor / Info) + 근거
       - Critical: 채널 0~99 범위 위반, 잘못된 `setCH` 호출, 검색/선호 데이터 손상
       - Major: README 시나리오 1~6 중 핵심 경로 실패
       - Minor: 경계·A시나리오 단건, 리팩토링 회귀
       - Info: 테스트명·로그·문서 불일치, `std::cout` 관련

    4) **최소 변경 수정 방안** (C++17)
       - `include/TVController.h` (필요 시 `remoteKey.h`)만 수정하는 **최소 diff** 제안
       - **금지**: `Tuner.h` 수정, 테스트 요구사항 왜곡을 위한 `TVControllerTest.cpp` 무분별 변경
       - 테스트가 SSOT와 맞고 생산 코드만 틀린 경우 → 생산 코드만 수정
       - Mock 기대가 requirements와 불일치한 경우 → 해당 테스트만 수정하고 이유 명시
       - Samsung 저작권 헤더 유지

    5) **회귀 범위**
       - 동일 영역(숫자/선호/검색/업다운)에서 추가로 깨질 수 있는 `TEST_F` 목록

[F] 출력 형식
    1. 실패별 분석 표 (위 1~3항)
    2. **unified diff** 형태 수정 제안 (`TVController.h` / `remoteKey.h` / 필요 시 테스트 1건)
    3. **Green 확인 절차** (실행 후 결과 보고):
       ```
       cmake --build build
       ctest --test-dir build --output-on-failure
       ```
       - `TunerTest` + `TVControllerTest` 전체 통과 여부
       - 수정 전/후 실패 개수
```

## 사용 팁

1. GMock 실패는 `Actual function call count doesn't match EXPECT_CALL` 형태가 많습니다. 프롬프트에 **전체 `-V` 로그**를 넣는 것이 좋습니다.
2. `InSequence` / `addFavorites` / `runSearch` 헬퍼 때문에 **테스트 셋업 오류**가 생기기 쉬우므로, 프롬프트의 “생산 vs 테스트 vs Mock” 구분이 중요합니다.
3. `Prompting/05.테스트실행_결함분석-Prompt.md`로 보관하려면 위 블록을 그대로 저장하면 됩니다.

원하시면 “로그 없이 실행부터 포함” 버전만 짧게 따로 정리해 드리겠습니다.

## 복사용 프롬프트

```
@test/TVControllerTest.cpp
@test/TunerTest.cpp
@include/TVController.h
@include/Tuner.h
@include/remoteKey.h
@docs/requirements_analysis.md
@docs/test_plan.md
@README.md
@CMakeLists.txt
@.cursorrules

[P] 회귀 테스트(Approval / Golden Master) 설계 전문가입니다. C++에서 GTest + 파일 스냅샷으로 대량 시나리오 회귀를 안전하게 잠그는 패턴에 익숙합니다.

[C] TDD_TV_Init (C++17, Google Test/Google Mock, CMake, `gtest_discover_tests`)
    - 생산: `TVController::pushButton(remoteKey)` → (선택) `std::cout` 로그 + `Tuner` API 호출
    - 기존 단위 테스트: `test/TVControllerTest.cpp` — GMock `EXPECT_CALL` (39건+, **유지·Green 유지**)
    - SSOT 시나리오: `README.md` 1~6, `docs/requirements_analysis.md` §6 (`1-1`~`6-4`, `A1`~`A8`)
    - **수정 금지**: `include/Tuner.h`
    - Gilded Rose의 `TexttestFixture.cpp`에 해당하는 **신규** Golden Master 드라이버를 이 프로젝트에 맞게 설계
    - 참고: 단위 테스트에서는 `std::cout` 미검증이나, Golden Master는 **회귀 스냅샷** 목적으로 stdout 캡처를 **선택적으로** 허용

[T] TexttestFixture 스타일의 **Golden Master 회귀 안전장치**를 설계·구현해줘.

    **0) Golden 대상 정의 (2계층, 둘 다 또는 1계층 선택 시 근거 명시)**

    | 계층 | 캡처 내용 | 용도 |
    |------|-----------|------|
    | **A (권장·Primary)** | `FakeTuner`(또는 RecordingTuner)가 기록한 **행위 트랜스크립트**: `setCH`, `getCurrentCH`, `seekCH` 호출 순서·인자 | README/requirements와 1:1, 로케일·공백 영향 적음 |
    | **B (선택·Secondary)** | `std::cout` 리다이렉트 텍스트 (`현재 설정하는 채널 : …`) | UI/로그 회귀, Gilded Rose Texttest 유사 |

    - 트랜스크립트 한 줄 예: `setCH 12` / `getCurrentCH -> 6` / `seekCH -> 4`
    - 시나리오 입력은 **리모컨 키 시퀀스**로 기술 (예: `1 OK`, `4 5 6 OK`, `CH_SEARCH`, `CH_UP`)

    **1) expected 출력 파일 생성·보관 전략**
    - 디렉터리: `test/golden/` (또는 `test/approval/`)
    - 파일명: `README_1_digit_ok.golden`, `scenario_1_3.golden`, `TC_5_3_wrap_99_up.golden` 등 (시나리오 ID 추적 가능)
    - 최초 생성: `--gtest_filter=GoldenMaster.*` + 환경변수 `UPDATE_GOLDEN=1` 시 actual→파일 저장
    - 정상 CI: `UPDATE_GOLDEN` 없이 actual vs golden **바이트/줄 단위 비교**
    - golden 변경 시: PR에 diff 리뷰, 의도적 갱신만 `UPDATE_GOLDEN` 사용
    - `.gitattributes` / 줄바꿈: LF 고정 권장 (Windows CRLF 이슈 방지)

    **2) Google Test에서 파일 비교 테스트 구현**
    - 신규: `test/GoldenMasterTest.cpp` (+ 필요 시 `test/GoldenMasterFixture.cpp` / `include/FakeTuner.h` 또는 `test/RecordingTuner.h`)
    - `TEST_F(GoldenMasterTest, Scenario_1_1_OneDigitThenOk)` 형태로 README §6 시나리오 **최소 1-1~6-4 전부** 커버 (A1~A8 중 경계 3건 이상 추가 권장)
    - Given: FakeTuner 초기 채널·`seekCH` 시퀀스 스텁
    - When: `pushButton` 시퀀스 실행
    - Then: 트랜스크립트(± stdout) 문자열 == `test/golden/<name>.golden`
    - 헬퍼: `readGolden(path)`, `writeGoldenIfUpdate(path, actual)`, `ASSERT_EQ` 또는 실패 시 **unified diff** 출력
    - 기존 `TVControllerTest`와 **독립** 타깅 (Mock 테스트 깨지지 않게)

    **3) CMake / ctest 통합**
    - `add_executable(GoldenMasterTest test/GoldenMasterTest.cpp …)`
    - `target_link_libraries(… GTest::gtest_main)` (GMock 불필요 시 생략 가능)
    - `gtest_discover_tests(GoldenMasterTest)`
    - (선택) `ctest -L golden`용 `LABELS golden` 또는 별도 `add_test(NAME golden_master …)`
    - golden 파일을 빌드 트리에 복사하지 말고 **소스 트리 `test/golden/`** 를 WORKING_DIRECTORY로 참조
    - 실행 예:
      ```
      cmake -B build && cmake --build build
      ctest --test-dir build --output-on-failure
      ctest --test-dir build -R GoldenMaster
      set UPDATE_GOLDEN=1 && build\GoldenMasterTest.exe
      ```

    **4) CI에서 자동 실행 구성**
    - 신규: `.github/workflows/ci.yml` (없을 경우 생성)
    - 단계: checkout → cmake configure/build → `ctest --output-on-failure`
    - `TunerTest` + `TVControllerTest` + `GoldenMasterTest` **전부 Green**이 merge 조건
    - `UPDATE_GOLDEN`은 CI에서 **사용 금지** (golden 불일치 시 실패로 회귀 감지)
    - (선택) PR 코멘트에 실패한 golden diff 요약

    **5) 운영·거버넌스**
    - Golden Master vs GMock 단위 테스트 역할 분리 문서 5줄 (`docs/golden_master.md` 신규 권장)
    - 리팩토링 시: GMock 테스트가 행위 계약, Golden이 **시나리오 전체 스냅샷** 잠금
    - `Tuner.h` / `TunerTest.cpp` 미수정

[F] 산출물 (디스크에 반영 + 실행 검증)
    1. **테스트 코드**: `test/GoldenMasterTest.cpp`, (필요 시) `include/FakeTuner.h` 또는 `test/RecordingTuner.h`
    2. **golden 파일**: `test/golden/*.golden` (README 1~6 + 경계 샘플)
    3. **CMakeLists.txt** 수정안 적용
    4. **CI**: `.github/workflows/ci.yml` (또는 기존 워크플로에 job 추가)
    5. **실행 방법** (README 스니펫 수준):
       - 일상 개발: `ctest`
       - golden 갱신: `UPDATE_GOLDEN=1` + 필터 실행
       - 실패 시 diff 확인 절차
    6. `cmake --build build && ctest --test-dir build` **전체 Green** 결과 보고
```
