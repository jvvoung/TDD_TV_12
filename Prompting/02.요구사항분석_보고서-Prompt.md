## Turn 1 — 요구사항 정밀 해석 (SSOT 문서)

### User

```
@README.md

[P] 시니어 C++ QA 엔지니어 관점에서, TDD로 구현·검증할 수 있도록 요구사항을 정밀하게 해석합니다.

[C] TDD_TV_Init 프로젝트 (C++17, CMake, Google Test/Google Mock)
    - 목표: 리모컨 입력 → TVController → Tuner(`setCH`/`getCurrentCH`/`seekCH`) 연동
    - 요구사항 원문: `README.md`
    - 외부 제공(수정 금지): `Tuner` 인터페이스, 채널은 `std::string`으로 0~99
    - 구현·테스트 대상: `TVController`, `remoteKey` 확장
    - Tuner는 항상 정확 동작 가정; Controller 테스트는 Mock/Fake (`TunerTest.cpp` 패턴 참고)
    - `TVController.h`의 `std::cout` 로그는 검증 대상 아님
    - 현재 스켈레톤: `remoteKey`는 KEY_1·KEY_OK만 존재, README의 나머지 키는 미구현

[T] `README.md`와 기존 헤더·테스트를 교차 검토하여, C++ 구현 관점에서 요구사항을 재정리해줘.

    1) 기능 영역별 비즈니스 규칙 표
       - 숫자 입력·확인(채널 직접 입력)
       - 선호 채널 추가/삭제(토글)
       - 다음 선호 채널(순환 포함)
       - 채널 검색(전체 스캔·결과 저장)
       - 채널 업/다운 — 검색 결과 없음(±1, 0↔99 래핑)
       - 채널 업/다운 — 검색 결과 있음(저장 목록 내 이전/다음, 래핑)
       각 행: 트리거(키) | 전제조건 | 동작 | Tuner 호출 | 상태 변경

    2) `README.md` 모호·누락 명세 정리 (17항, 해석 A/B, 권장 구현 가정, acceptance)
    3) 문자열·숫자 처리 주의점 (`std::string`, `stoi`, 0~99)
    4) 경계값·예외 조건 목록
    5) `remoteKey` enum · `TVController::pushButton` 설계 힌트
    6) Google Test 기준 테스트 시나리오 목록 (README 1~6 + 경계)
    7) 구현 범위 밖·가정

[F] Markdown (표 + 번호 목록). **파일로 저장**: 프로젝트 루트 `docs/requirements_analysis.md`
    - `docs/` 폴더가 없으면 생성
    - 문서 상단: 프로젝트명, 분석 일자, 참조 파일 목록
    - 표는 GitHub에서 읽기 쉬운 Markdown 표 사용
    - README에 없는 기능은 “Out of scope”로 명시
```

### Assistant

- `README.md`, `include/Tuner.h`, `include/TVController.h`, `include/remoteKey.h`, `test/TunerTest.cpp`, `test/TVControllerTest.cpp`, `CMakeLists.txt` 교차 검토.
- `docs/` 디렉터리 생성 후 상세 명세 문서 작성 (327행).

**핵심 의사결정 (TDD용)**

| 영역 | 권장 가정 |
|------|-----------|
| 숫자 입력 | 1자리=`KEY_OK` 확정; 2자리=두 번째 숫자 즉시 `setCH`; 선행 `0` 대체 |
| `4,5,6` | `45` 확정 후 `"6"` 대기; 숫자·OK 외 키→버퍼 무효화 |
| 채널 검색 | `seekCH()` until `""` (`TunerTest.cpp` 관례) |
| 업/다운 | `searchResults.empty()`면 ±1 래핑, 아니면 검색 목록 탐색 |
| 다음 선호 | 현재보다 큰 최소값, 없으면 최소값 로테이션 |

**산출물**

|------|------|
