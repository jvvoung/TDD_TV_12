## Turn 1 — 단위 테스트 계획서 (SSOT 문서)

### User

```
@README.md
@docs/requirements_analysis.md
@include/Tuner.h
@include/TVController.h
@include/remoteKey.h
@test/TunerTest.cpp
@test/TVControllerTest.cpp
@CMakeLists.txt
@.cursorrules

[P] 시니어 QA 리드입니다. TDD 사이클(Red→Green→Refactor)과 Google Mock 기반 단위 테스트 설계에 익숙합니다.

[C] TDD_TV_Init 프로젝트 (C++17, CMake 3.14+, Google Test/Google Mock v1.14.0, `gtest_discover_tests`)
    - SSOT: `docs/requirements_analysis.md` (비즈니스 규칙 §1, 모호성 §2, 경계 E1~E15, 시나리오 §6.1~6.2)
    - 구현 대상: `TVController`, `remoteKey` / 수정 금지: `Tuner` 인터페이스
    - 채널 도메인: `std::string` 0~99; Controller 테스트는 Mock/Fake (`TunerTest.cpp` 패턴)
    - 기존 타깅: `TunerTest`, `TVControllerTest` (`CMakeLists.txt`)
    - 검증 제외: `std::cout` 로그, Tuner 실구현·`TunerTest.cpp` 본문 수정
    - 커버리지: 현재 CMake에 gcov/lcov 미설정 → 계획서에 **선택 적용**으로 기술

[T] 아래 항목을 포함한 **테스트 계획서**를 작성해줘.

    1) 테스트 전략 요약
       - 단위 테스트 범위(In scope / Out of scope)
       - Mock vs Fake 사용 기준 (`Tuner` 계약 검증 vs Controller 행위 검증)
       - TDD 진행 순서(우선순위 P0/P1/P2): README 시나리오 1→6, 그다음 경계·모호 해소

    2) 테스트 구조·fixture 설계
       - `TEST_F` 기반: `TVControllerTest` fixture (`MockTunerForController`, `TVController`)
       - `TEST_P` / `INSTANTIATE_TEST_SUITE_P` 적용 후보 (채널 래핑, 유효 숫자 조합, `TunerTest.cpp`의 Valid/Invalid 채널 패턴 참고)
       - 파일·타깅 제안 (`test/TVControllerTest.cpp` 확장 vs 분리) 및 CMake 등록

    3) 단위 테스트 범위·우선순위 표
       - 기능 영역(§1.1~1.6)별: 테스트 ID | 우선순위 | 대응 requirements §6 시나리오 번호(1-1, 2-1, A1 등) | 검증 포인트 | Mock 기대 요약

    4) 경계값 케이스 목록 (표)
       - 채널: `0`, `1`, `99`, `0↔99` 래핑(업/다운, 검색 없음)
       - 숫자 입력: 1자리+OK, 2자리 즉시 확정, `0`+`7`→`7`, `9`,`9` 후 세 번째 숫자, 빈 버퍼+OK
       - 선호: 0개/1개/다수, 로테이션(현재 `56`→`1`)
       - 검색: `seekCH` 즉시 `""`, 단일 결과 `{6}`, 목록 외 현재 채널(`15`)
       - 분기: `searchResults.empty()` true/false에 따른 업/다운

    5) 예외·특이 케이스 목록
       - 미확정 버퍼 + 비숫자·비OK 키 → 무효화 (`4`,`5`,`6` 후 UP 등)
       - Controller 선검증으로 `setCH` 미호출(무효 채널)
       - `getCurrentCH` 무효 문자열 시 no-op (requirements E14)
       - `KEY_NEXT_FAVORITE` 선호 없음, `setCH` Times(0) 시나리오
       - Tuner `invalid_argument`는 `TunerTest` 영역, Controller 테스트와 역할 분리

    6) 시나리오 ↔ 테스트 케이스 매트릭스
       - `requirements_analysis.md` §6.1(1-1~6-4), §6.2(A1~A8) 각각에 대해:
         - 제안 `TEST_F`/`TEST_P` 이름(영문, Given_When_Then 스타일)
         - Given / When / Then (1줄)
         - `EXPECT_CALL` 핵심(메서드, Times, Return/Throw)

    7) TDD 실행 계획 (스프린트/단계)
       - Phase별: 추가할 테스트 목록 → 최소 구현 → 리팩토링 체크포인트
       - 각 Phase 완료 기준: `ctest` Green, 관련 시나리오 ID 전부 통과

    8) 커버리지 목표·측정·개선 전략
       - 목표: `TVController`·`remoteKey` 관련 코드 **라인 커버리지 90%+** (권장, 조정 가능)
       - 현재: gcov/lcov 미설정 → CMake 옵션 예시(`-fprofile-arcs -ftest-coverage`, `lcov`/`genhtml`) **부록**으로만 제시
       - 측정 범위: `include/TVController.h`, `include/remoteKey.h` / 제외: `Tuner.h`, 로그, `build/`
       - 미커버 구간 대응: 분기(검색 유/무), 버퍼 상태, 선호 토글 등에 대한 추가 `TEST_P` 제안

    9) 리스크·미결정 사항
       - requirements §2·E5·A8 등 **테스트에서 하나로 고정할** 항목과 결정안
       - 내부 상태(`favoriteChannels`, `searchResults`) 직접 검증 불가 시 호출 순서만으로 검증하는 한계

[F] Markdown 문서 (표 + 번호 목록). **파일로 저장**: 프로젝트 루트 `test_plan.md`
    - `docs/` 폴더가 팀 규칙상 문서 SSOT이면 `docs/test_plan.md`로 저장해도 됨(저장 경로를 문서 상단에 명시)
    - 상단: 프로젝트명, 작성일, 참조 문서(`requirements_analysis.md`, `README.md`)
    - §6 시나리오 ID와 계획서 테스트 ID를 1:1로 추적 가능하게
    - 실행 명령 예: `cmake -B build && cmake --build build && ctest --test-dir build`
```

### Assistant

- `README.md`, `docs/requirements_analysis.md`, 헤더 3종, `TunerTest.cpp`, `TVControllerTest.cpp`, `CMakeLists.txt`, `.cursorrules` 교차 검토.
- 팀 문서 SSOT 규칙에 따라 **`docs/test_plan.md`** 에 상세 계획서 작성 (441행).
