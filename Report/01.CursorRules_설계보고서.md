## 1. 프로젝트 개요

본 프로젝트는 셋탑박스 환경에서 **리모컨 키 입력**을 받아 **채널(0~99)** 을 관리하고, 외부 업체가 제공하는 **Tuner** 인터페이스를 통해 실제 채널을 설정하는 `TVController` 모듈을 **TDD(Test-Driven Development)** 로 구현하는 실습이다.

- **우리가 구현·테스트하는 대상**: `TVController`, `remoteKey` 확장
- **외부 제공(수정 금지)**: `include/Tuner.h`의 `Tuner` 가상 인터페이스
- **요구사항 출처**: 프로젝트 루트 `README.md`
- **AI 개발 가이드**: 프로젝트 루트 `.cursorrules` (Cursor IDE가 워크스페이스 규칙으로 자동 참조)

## 2. 시스템 구성

### 2.1 아키텍처

```
[리모컨 센서] → remoteKey → TVController::pushButton()
                                    ↓
                              Tuner* (DI)
                                    ↓
                    setCH / getCurrentCH / seekCH
```

- `TVController`는 생성자 주입(`Tuner*`)으로 Tuner에 의존한다.
- Tuner는 항상 정확히 동작한다고 가정하며, 단위 테스트에서는 **Mock** 또는 **Fake**로 대체한다.
- 채널 값은 Tuner API와 주고받을 때 **`std::string`** 형식을 사용한다 (예: `"12"`, `"0"`).

### 2.2 Tuner 인터페이스 (외부 계약)

| 메서드 | 역할 |
|--------|------|
| `seekCH()` | 현재 채널에서 증가 방향으로 시청 가능 채널 검색 후 변경·반환 |
| `setCH(const std::string&)` | 지정 채널로 변경 |
| `getCurrentCH()` | 현재 채널 문자열 반환 |

유효하지 않은 채널 입력 시 `std::invalid_argument`를 던질 수 있으며, 이는 `test/TunerTest.cpp`의 Mock 테스트로만 검증한다.

### 2.3 디렉터리 구조

```
TDD_TV_Init/
├── .cursorrules          # Cursor AI 개발 규칙
├── CMakeLists.txt        # 빌드·테스트 타깃 정의
├── README.md             # 기능 명세
├── include/
│   ├── Tuner.h           # 외부 Tuner 인터페이스 (수정 금지)
│   ├── TVController.h    # Controller (구현 대상)
│   └── remoteKey.h       # 리모컨 키 enum
├── test/
│   ├── TunerTest.cpp     # Tuner Mock 사용법·계약 참고용
│   └── TVControllerTest.cpp
└── Report/
    └── TDD_TV_Init_보고서.md   # 본 문서
```

별도 `src/` 디렉터리는 없으며, 구현은 `include/*.h` 헤더 중심으로 유지한다.

## 3. 기능 요구사항 (`README.md` 요약)

| # | 기능 | 핵심 동작 |
|---|------|-----------|
| 1 | 숫자 버튼 + 확인 | `1`+확인→1번, `1`→`2`→12번, 연속 입력 시 12→34, `4` `5` `6` 후 확인/기타 키 처리, `0` `7`→7번 |
| 2 | 선호채널 추가 | 시청 중 토글(미등록→추가, 등록→삭제) |
| 3 | 다음 선호 채널 | 목록 내 현재보다 큰 최소값, 최대값 이후 로테이션(예: 56→1) |
| 4 | 채널 검색 | 검색 버튼 시 `seekCH()` 반복으로 시청 가능 채널 전체 저장 |
| 5 | 업/다운 (검색 결과 없음) | ±1, 99→업→0, 0→다운→99 래핑 |
| 6 | 업/다운 (검색 결과 있음) | 저장 목록 내 다음/이전, 현재 채널이 목록 밖이면 순환 |

리모컨 키: 숫자 0~9, 채널 업/다운, 확인, 채널검색, 선호채널추가, 다음선호채널.

## 4. 빌드 및 테스트 환경

### 4.1 CMake 설정

- C++17 (`CMAKE_CXX_STANDARD 17`)
- `FetchContent`로 Google Test / Google Mock **v1.14.0** 다운로드
- `include_directories(include)`
- `gtest_discover_tests`로 CTest 연동

### 4.2 테스트 타깃

| 타깃 | 소스 | 용도 |
|------|------|------|
| `TunerTest` | `test/TunerTest.cpp` | Tuner 계약·Mock 패턴 참고 (5개 테스트 스위트) |
| `TVControllerTest` | `test/TVControllerTest.cpp` | Controller TDD (스켈레톤) |

### 4.3 빌드·실행 방법

```bash
cmake -S . -B build
cmake --build build
ctest --test-dir build --output-on-failure
```

개별 실행 예: `./build/TunerTest`, `./build/TVControllerTest`

## 5. `.cursorrules` 작성 (Cursor AI 개발 규칙)

### 5.1 작성 배경 및 목적

TDD_TV_Init은 **레거시·스켈레톤 코드를 TDD로 확장**하는 실습이며, Cursor AI를 활용한 보조 개발 시 다음 문제가 반복될 수 있다.

- 외부 계약인 `Tuner.h`를 수정하거나 Tuner 실구현을 새로 추가하는 경우
- `README.md`에 없는 동작을 임의로 넣는 경우
- `std::cout` 로그를 테스트 검증 대상으로 삼는 경우
- `build/`, `_deps/` 등 빌드 산출물을 커밋·수정하려는 경우

이를 방지하고, **임베디드/셋탑 TV 도메인에 맞는 TDD 절차**를 AI가 매 세션마다 동일하게 따르도록, 프로젝트 루트에 **`.cursorrules`** 파일을 작성·배치하였다 (2026-05-19).

| 항목 | 내용 |
|------|------|
| 파일 경로 | `TDD_TV_Init/.cursorrules` |
| 형식 | Markdown (`##` 섹션 + 불릿, 한국어 위주·식별자는 영문) |
| 분량 | 약 107줄 (실무 참고용, 과도한 장문 지양) |
| 적용 대상 | Cursor IDE 내 본 워크스페이스의 AI 에이전트·채팅 |

### 5.2 작성 시 반영한 입력 자료

규칙 문서는 아래 저장소 요소를 교차 검토하여 도출하였다.

| 입력 자료 | 반영 내용 |
|-----------|-----------|
| `README.md` | 6개 기능 시나리오, 채널 0~99, 리모컨 키 목록 |
| `include/Tuner.h` | 외부 Tuner API 3종, 수정 금지 계약 |
| `include/TVController.h` | `Tuner*` DI, `processingCH`, `pushButton`, 디버그 로그 비검증 |
| `include/remoteKey.h` | enum·`to_string` 확장 패턴 |
| `test/TunerTest.cpp` | `TEST_F`/`TEST_P`, `EXPECT_CALL`, `MOCK_METHOD`, invalid 채널 Mock |
| `CMakeLists.txt` | C++17, FetchContent GTest v1.14.0, `gtest_discover_tests` 패턴 |
| 프로젝트 구조 | `include/` + `test/`, `src/` 없음 |

### 5.3 `.cursorrules` 문서 구성 (7개 섹션)

파일은 아래 7개 주제로 구성되며, 각 섹션은 Cursor AI의 작업 범위·금지 사항을 명시한다.

| # | 섹션 제목 | 핵심 규칙 |
|---|-----------|-----------|
| 1 | 프로젝트 개요 | 구현 대상(`TVController`, `remoteKey`) vs 외부 제공(`Tuner`) 구분 |
| 2 | 프로젝트·빌드 | C++17, `include/` 경로, `ctest`/GTest 타깃, 새 테스트 `add_executable` + `gtest_discover_tests` 템플릿 |
| 3 | 절대 규칙 | `Tuner.h` 시그니처 변경 금지, Mock/Fake만 허용, 채널 0~99, Samsung 저작권 헤더 유지 |
| 4 | TDD·구현 규칙 | Red→Green→Refactor, Green 유지 시에만 리팩토링, README 6시나리오 기준, 미명세 동작 금지 |
| 5 | 테스트 규칙 | GTest+GMock, Given-When-Then 이름, `EXPECT_CALL` 검증, 로그 assert 금지, 시나리오별 최소 1테스트·경계값 |
| 6 | 코드 스타일·구조 | 기존 네이밍, named constant 권장, 헤더 중심 구현, `remoteKey`/`to_string` 동기화 |
| 7 | AI 작업 시 금지·주의 | `build/`·`_deps/` 미수정, Tuner 실구현 금지, 대규모 리네이밍 금지, 커밋·PR은 사용자 요청 시만 |
| (부가) | 커버리지 (선택) | gcov/lcov 미설정 — 별도 요청 시에만 제안 |
| (부가) | 작업 체크리스트 | README 확인 → 실패 테스트 → 최소 구현 → `ctest` Green → 리팩토링 → 시나리오 누락 점검 |

### 5.4 설계 시 우선한 원칙

작성 과정에서 다음 원칙을 우선 적용하였다.

1. **계약 분리** — Tuner(외부)와 Controller(자체 구현) 경계를 문서 최상단에 고정하여, AI가 Tuner 구현·시그니처 변경을 시도하지 않도록 함.
2. **명세 단일 출처** — 동작 정의는 `README.md`만 인정; 불명확 시 테스트 이름·주석에 가정을 적도록 규정.
3. **테스트 스타일 고정** — `TunerTest.cpp`를 공식 참조 예제로 지정해 `TEST_P`, `INSTANTIATE_TEST_SUITE_P`, `Throw` 패턴을 Controller 테스트에도 이식.
4. **실습 친화 분량** — 80~150줄 내외로, 매일 열어볼 수 있는 체크리스트·CMake 스니펫만 포함.
5. **로그·산출물 배제** — `TVController`의 `std::cout`과 `build/` 디렉터리를 AI 작업·검증 대상에서 명시적으로 제외.

### 5.5 Cursor에서의 활용 방법

- `.cursorrules`는 **프로젝트 루트**에 두면 Cursor가 워크스페이스 규칙으로 읽는다.
- 새 채팅·에이전트 작업 시 별도 프롬프트 없이도 위 규칙이 컨텍스트에 반영된다.
- 규칙 변경 시 `.cursorrules`만 수정·커밋하면 팀 전체 AI 동작을 일괄 갱신할 수 있다.
- 본 보고서(`Report/`)는 사람이 읽는 **작성 배경·구조 설명**이고, `.cursorrules`는 AI가 따르는 **실행 규칙 원문**이다.

### 5.6 README 시나리오 ↔ `.cursorrules` 매핑

`.cursorrules`의 TDD·테스트 섹션은 `README.md` 6개 시나리오와 1:1로 대응하도록 작성되었다.

| README # | 시나리오 | `.cursorrules`에서 요구하는 테스트·구현 |
|----------|----------|--------------------------------------|
| 1 | 숫자 + 확인 | 연속 숫자, 12→34, 45/6 무효화 등 |
| 2 | 선호채널 추가 | 토글(추가/삭제) |
| 3 | 다음 선호 채널 | 상향 최소값, 로테이션 |
| 4 | 채널 검색 | `seekCH` 반복·결과 저장 |
| 5 | 업/다운 (검색 없음) | ±1, 0↔99 래핑 |
| 6 | 업/다운 (검색 있음) | 저장 목록 내 이전/다음 |

각 시나리오마다 **최소 1개 이상**의 테스트를 권장하도록 규정되어 있다.

### 5.7 기대 효과

- AI 보조 개발 시 Tuner 경계·Mock 패턴·README 시나리오를 반복적으로 어기지 않도록 한다.
- 실습 참가자·리뷰어가 **동일한 TDD 절차**(Red→Green→Refactor)와 테스트 우선 순서를 공유할 수 있다.
- `.cursorrules`와 본 보고서를 함께 두면, **규칙 원문(AI용)** 과 **작성 근거·맥락(사람용)** 을 분리하여 유지보수할 수 있다.

## 7. TDD 적용 계획

### 7.1 권장 진행 순서

1. **숫자 + 확인** — `remoteKey` 0~9·`KEY_OK` 확장, `setCH` Mock 검증, `1`+확인→`"1"` 등
2. **연속 숫자·무효화** — README 1번 시나리오 나머지
3. **업/다운 (검색 없음)** — 경계 0/99 래핑
4. **채널검색 + 업/다운 (검색 있음)** — `seekCH` Mock 연동
5. **선호채널·다음 선호** — 내부 목록 상태 관리

### 7.2 테스트 작성 원칙

- Given-When-Then이 드러나는 `TEST_F` / `TEST` 이름 (한글·영문 가능)
- Controller 테스트마다 `EXPECT_CALL(mock, setCH("…"))` 등 Tuner 호출 검증
- 경계값: 0, 99, 0↔99 래핑, invalid 채널은 Mock `Throw` 패턴만 사용

### 7.3 리팩토링 시점

- 각 시나리오별 테스트 Green 확인 후 `MIN_CHANNEL` / `MAX_CHANNEL` 상수 추출, `pushButton` switch 정리
- `tuner->setCH(processingCH)` 주석 해제 및 `processingCH` 초기화 로직 정리

## 8. 제약 사항 및 유의점

1. **`include/Tuner.h` 수정 불가** — 외부 업체 계약
2. **Tuner 실구현 파일 금지** — 테스트 더블만 허용
3. **디버그 로그** — `TVController`의 `std::cout`은 동작 확인용이며 테스트 assert 대상 아님
4. **빌드 산출물** — `build/`, `_deps/`는 버전 관리·AI 수정 대상에서 제외
5. **커버리지** — CMake에 gcov/lcov 미설정; 필요 시 별도 요청·브랜치에서 도입

## 9. 결론 및 향후 과제

TDD_TV_Init은 셋탑 TV 채널 제어 도메인에 TDD를 적용하기 위한 잘 정리된 스켈레톤이다. `TunerTest.cpp`는 Mock 기반 테스트 패턴의 참고 자료로 충분하다.

## 부록 C. `.cursorrules` 원문 섹션 목차

AI·개발자가 원문을 열 때 참고할 목차이다. 전문은 프로젝트 루트 `.cursorrules`를 본다.

```
1. 프로젝트 개요
2. 프로젝트·빌드          ← CMake, ctest, 새 테스트 타깃 템플릿
3. 절대 규칙              ← Tuner.h, Mock/Fake, 0~99, 저작권 헤더
4. TDD·구현 규칙          ← Red→Green→Refactor, README 6시나리오
5. 테스트 규칙            ← GMock, EXPECT_CALL, 경계값, 로그 비검증
6. 코드 스타일·구조       ← remoteKey, 헤더 중심, named constant
7. AI 작업 시 금지·주의   ← build/, 커밋·PR, 리네이밍
   커버리지 (선택)
   작업 체크리스트 (6단계)
```

### 부록 C-1. 기능 추가 시 AI·개발자 공통 체크리스트

`.cursorrules` 말미에 정의된 6단계이다.

1. `README.md` 해당 절 확인  
2. 실패하는 테스트 1개 작성 (Mock/Fake로 Tuner 기대 설정)  
3. `TVController` / `remoteKey` 최소 변경으로 Green  
4. `ctest` 또는 해당 GTest 타깃으로 전체 Green 확인  
5. Green 유지하며 리팩토링 (중복 제거, 상수 추출)  
6. 관련 README 시나리오 테스트 누락 없는지 확인
