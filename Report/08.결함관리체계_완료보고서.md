## 1. 보고 목적

`Report/05`에서 **사건별 RCA·최소 diff** 형식으로 회귀 분석을 수행했고, `Report/06`·`07`에서 **Golden Master 26건** 및 **리팩토링**까지 반영해 통합 검증 규모가 **78건**으로 확대되었다. 이에 따라 결함을 **일관되게 분류·등록·보고**할 운영 체계가 필요했다.

본 보고서는 다음을 기록한다.

- `docs/defect_report.md` 신규 작성(정책·템플릿·메트릭·문서 연계)
- `docs/defect_list.md` v1.1 갱신(78건·Golden·정책 문서 참조)
- 기존 Report·docs와의 역할 분리 및 동기화 규칙
- 현재 스냅샷(Open 0, OBS-001) 및 후속 운영 권장

## 4. 결함 분류 체계 (요약)

상세는 [`docs/defect_report.md`](../docs/defect_report.md) §1을 SSOT로 한다.

### 4.1 Severity (4종, 기존 유지)

| 값 | 의미 |
|----|------|
| Critical | 채널 0~99 위반, 잘못된 `setCH`, 검색/선호 데이터 손상 |
| Major | README 시나리오 1~6 핵심 경로 실패 |
| Minor | 경계·A시나리오, 리팩토링 회귀 |
| Info | 문서·로그·GMock 경고(테스트 통과) |

### 4.2 ItemType (5종)

| ItemType | 대상 | 수정 |
|----------|------|------|
| Production | `TVController.h`, `remoteKey.h` | 본 프로젝트 |
| Test | `TVControllerTest.cpp`, Mock | 본 프로젝트 |
| Contract | `Tuner.h` | **수정 금지**, 기록·외부 추적 |
| Environment | CMake/MSVC/CRT | 빌드·CI |
| Documentation | README·requirements·Report | 문서 |

### 4.3 FunctionalArea (보조 태그, 6종)

`Digit` · `Favorite` · `NextFavorite` · `Search` · `UpDownLinear` · `UpDownSearch`

결함 등록 시 **시나리오 ID**(`1-4b`, `6-3`, `A8`, `E14` 등)와 함께 1개 이상 태그를 부여한다.

### 4.4 Severity × ItemType 매트릭스

5행(ItemType) × 4열(Severity) 표에 **대표 결함 예시 1줄 + 시나리오 ID**를 칸마다 정의했다.  
예: Production × Major → `4,5,6` 후 `CH_UP` 시 `6` 미무효화 (**1-4b**).

### 4.5 ID·Status

| ID | 용도 |
|----|------|
| `DEF-###` | 재현 가능 결함 (GMock Red 또는 golden diff) |
| `OBS-###` | 관찰·Info (Green, 로그·경고만) |
| `REQ-###` | 명세 이슈 (선택) |

Status: `Open` → `In Progress` → `Fixed` → `Verified (Closed)` / `Won't Fix` / `Deferred`  
Phase 태그: `요구분석` | `구현` | `단위테스트` | `회귀` | `Golden` | `리팩토링`

## 5. 결함 보고 절차

### 5.1 보고 템플릿

[`defect_report.md`](../docs/defect_report.md) §2에 **복사 가능한 Markdown 블록**을 두었다.

필수 필드: ID, Title, Severity, ItemType, FunctionalArea, Scenario ID, 재현(Steps), 기대(Expected), 실제(Actual), Root Cause, Fix, Verification, 연계(`Report/05` 절, `defect_list` 행, Issue #).

### 5.2 등록·해결 워크플로

```
[실패 발생]
    ├─► ctest / --gtest_filter / Golden diff 재현
    ├─► Report/05 §4 형식 RCA (사건)
    ├─► defect_list.md §3 행 추가 (DEF-###)
    └─► 수정 후 ctest Green → Status Verified → Closed

[관찰만 (Green)]
    └─► defect_list.md §4 (OBS-###)
```

### 5.3 검증 기준 (재확인)

| 수단 | 용도 |
|------|------|
| `EXPECT_CALL(setCH/getCurrentCH/seekCH)` | 단위 테스트 Then |
| `test/golden/*.golden` | 시나리오 트랜스크립트 (Golden) |
| `std::cout` | **결함 판단 제외** |
| `Tuner.h` / `TunerTest.cpp` | Contract — 본 프로젝트 **수정 금지** |

## 6. 품질 메트릭 수집 계획

[`defect_report.md`](../docs/defect_report.md) §3에 상세 정의. 요약:

| 메트릭 | 수집 |
|--------|------|
| 테스트 통과율 | `ctest --test-dir build` — 78건 기준 |
| 타깅별 통과 | `-R TunerTest` / `TVControllerTest` / `GoldenMaster` |
| Open 결함 수 | `defect_list.md` §1·§3 |
| 결함 발견 단계 | Phase 태그 |
| 결함 밀도 | Closed DEF / KLOC (`TVController.h`) |
| 커버리지 (선택) | gcov + lcov — `test_plan.md` §8, CMake 미설정 |
| Golden 불일치 | CI에서 `UPDATE_GOLDEN` **금지** |

C++ 커버리지는 `ENABLE_COVERAGE=ON` → `lcov` → `genhtml` 절차를 문서화했으며, JaCoCo·pytest-cov는 타 프로젝트 비교 참고로만 기술했다.

## 10. 결론

1. **완료**: 결함 **관리 체계**를 `docs/defect_report.md`로 문서화하고, **레지스트리** `defect_list.md`를 v1.1(78건·Golden)으로 동기화했다.
